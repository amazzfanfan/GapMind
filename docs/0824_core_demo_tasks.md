## 一、Demo 总原则

三条任务共同遵守以下规则：

- 输入资料使用脱敏、冻结、可追溯的 Workspace 快照；
- 论文证据、研究计划、报告和代码草稿严格分开；
- 没有证据时拒答或标记证据不足；
- 候选研究机会不是事实，必须经过人工确认；
- AI 生成的计划、报告和代码显示未确认状态；
- 代码静态检查不等于运行、实验复现或结果验证；
- 实时外部服务、缓存结果和冻结快照必须在 Demo 中明确标识。

## 二、任务 1：证据驱动的论文问答

### 任务目标

研究生/科研助理针对当前 GNN 资料提出一个概念、方法或实验问题，系统给出来源可追溯的回答；如果当前资料无法支持问题，系统必须明确说明证据不足。

### 建议问题类型

- 某方法解决什么问题，核心假设是什么？
- 两篇论文在方法、数据集、基线和指标上有什么差异？
- 当前资料能否支持一个绝对化结论？

### 输入

- 冻结 Workspace；
- 经过解析和索引的脱敏论文；
- 一个属于资料范围的问题；
- 一个故意超出资料范围或要求绝对结论的问题，用于展示 fail-closed。

### 操作路径

1. 进入目标 Workspace，确认资料范围和当前快照；
2. 在 Chat 中提出问题；
3. 查看回答、论文 `[En]` 引用和证据卡；
4. 打开一条证据，查看页码/段落或原文定位；
5. 追问一个澄清问题，展示多轮上下文；
6. 提出证据不足问题，展示拒答/补充资料提示。

### 必须展示

- 检索范围；
- 来源类型和论文标记；
- 引用与回答的对应关系；
- 证据不足时的明确状态；
- 不把代码草稿或研究计划标记成论文证据。

### 成功标准

- 回答中的关键事实都能回到真实论文来源；
- 多轮追问不会丢失当前 Workspace 约束；
- 无证据问题不会生成无来源的确定性结论；
- 用户能在合理时间内打开并理解引用证据。

### 失败路径

- 无命中：提示资料不足，建议缩小问题或补充资料；
- 检索服务失败：提示 retrieval_failed 和可重试动作；
- 引用质量不通过：不输出伪装成事实的回答；
- 资料类型不匹配：提示当前问题不在 Workspace 范围内。

## 三、任务 2：研究机会核验与 Critic 收窄

### 任务目标

研究生提出一个 GNN 研究想法，系统从 Workspace 论文、相似工作、反证和外部检索中形成候选，并通过 Critic 和 Evidence Gate 将候选交给导师/研究生人工确认。

### 输入

- 已冻结的 GNN 论文集；
- 一个明确的研究想法或问题；
- 至少一组支持方向和一组可能的相似/反证材料；
- 外部检索服务实时可用或对应的冻结结果快照。

### 操作路径

1. 从 Workspace 或 Discover 页面输入研究问题；
2. 启动 Discover，并展示 Planner 的研究轴/查询计划；
3. 查看 Evidence 阶段的支持证据和反证；
4. 查看 External Novelty 的实时、缓存或部分成功状态；
5. 查看 Opportunity 候选，不直接把它称为新颖结论；
6. 查看 Critic 的 `keep/narrow/reject` 理由；
7. 对 `narrow` 候选进行收窄补查；
8. 查看 Evidence Gate、独立全文数量、全文/元数据范围和 Evidence Passport；
9. 由用户执行确认、拒绝、编辑确认或延后。

### 必须展示

- Planner、Evidence、External、Opportunity、Critic、Gate 的阶段关系；
- 支持证据和反证分栏；
- 外部核验成功、部分成功、失败和未执行的区别；
- 候选、可确认、已验证和人工确认状态的区别；
- 用户确认记录不可被 AI 自动替代。

### 成功标准

- 系统输出的是可审阅候选，而不是未经证据支持的“新颖性结论”；
- 至少能展示一次 `narrow` 或 `needs_more_evidence` 分支；
- Gate 不通过时，用户知道缺少独立全文、支持证据或反证信息；
- 用户可以做出确认、拒绝、补查或延后决定。

### 失败路径

- S2/外部服务部分失败：保留已完成查询的审计，整体状态为 partial，不显示已完成核验；
- 支持证据不足：进入 needs_more_evidence；
- 仅有元数据无全文：降低证据等级，不作为全文支持；
- Critic reject：解释拒绝理由，并保留候选历史，不硬删除。

## 四、任务 3：研究计划与代码草稿辅助

### 任务目标

用户对研究候选进行人工确认或明确要求进入计划阶段，系统生成可审阅的研究计划和代码草稿，展示证据来源、实验要素、风险和静态检查结果。

### 输入

- 已确认或明确标记为待审阅的研究候选；
- 支持/反证证据和用户补充约束；
- 研究目标、数据集、基线、指标等已知信息；
- 允许的代码生成范围。

### 操作路径

1. 查看候选的 Evidence Passport 和人工状态；
2. 启动 Research Plan Agent；
3. 查看假设、研究问题、实验设计、数据集、基线、指标、消融、统计检验和风险；
4. 标记哪些字段来自论文、哪些是用户输入、哪些是模板建议或模型推断；
5. 用户确认或退回计划；
6. 在用户明确操作后启动 Code Generation Agent；
7. 查看文件清单、入口、依赖、README、测试、静态检查和计划覆盖；
8. 导出草稿，并明确代码尚未执行。

### 必须展示

- 研究计划是 AI 草稿还是人工确认产物；
- 计划字段的来源和证据；
- 研究假设的可证伪性；
- 代码静态检查的具体项目；
- “未执行/不代表实验复现”的明显提示；
- 版本、生成时间和输入资料快照。

### 成功标准

- 计划至少包含假设、数据集、基线、指标、风险和验证方式；
- 用户可以在人工确认前修改或驳回；
- 代码生成结果结构完整、路径安全、依赖和入口清楚；
- 没有把静态检查通过写成运行成功或实验结果成立。

### 失败路径

- 证据不足：计划保留未确认状态，不自动补写成事实；
- 缺失数据集/基线/指标：显示缺口，要求用户补充或接受“建议字段”标记；
- 代码生成失败：保留错误原因和候选修复，不生成虚假的成功状态；
- 用户未确认：不把计划或代码提升为正式长期资产。

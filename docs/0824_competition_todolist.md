# GapMind 比赛冲刺 Todo List

**制定日期**：2026-08-24
**适用分支**：`yx_dev`
**依据文档**：`docs/0824_competition_review.md`、`docs/XH-202620_面向一流学科建设的学科垂类大模型与创新应用开发.pdf`
**目标**：把已有工程能力收敛为一个可演示、可验证、可复现、可提交的学科垂类科研助手。
**执行原则**：先完成 P0 的比赛证据闭环，再做 P1 的得分增强，最后考虑 P2 的技术扩展。

本文是执行清单，不是功能愿望列表。每一个任务都必须有负责人、产出物和验收证据；没有验收证据的任务只能标记为“进行中”，不能视为完成。

## 一、使用说明

### 1. 状态标记

- `[ ]` 未开始
- `[~]` 进行中
- `[x]` 已完成并有证据
- `[!]` 被阻塞，需要外部输入或决策
- `[—]` 本版本明确不做，但要记录原因

### 2. 优先级规则

| 优先级 | 含义 | 执行规则 |
|---|---|---|
| P0 | 影响比赛基本得分、合规或现场稳定性的任务 | 必须在 P1/P2 前完成；没有验收证据不得进入最终提交 |
| P1 | 明显提升内容质量、用户体验、技术实现和商业化的任务 | P0 稳定后执行，按剩余时间选择高收益项 |
| P2 | 技术先进性或长期产品化增强项 | 只有在不影响 P0 交付时执行；不能抢占 Demo、用户验证和提交材料时间 |
| GATE | 阶段性放行条件 | 未通过时暂停后续阶段，先修复阻塞项 |

### 3. 当前基线

在开始任何修改前，先重新确认当前分支和工作区状态。审查时的基线如下，执行时必须重新验证：

- 分支：`yx_dev`；工作区存在用户已有的 `.gitignore` 修改、`deploy/`、根目录 `index.html`、比赛 PDF 等未提交/未跟踪内容，不能误删或覆盖。
- Alembic 迁移：当前代码记录的 head 为 `0024_chat_generation_observability`。
- 后端测试：`469 passed, 2 warnings`。
- 前端测试：`56 passed`。
- TypeScript 检查：通过。
- 前端构建：通过，但存在主包体积偏大的提示。
- ESLint：`0 errors, 14 warnings`。
- 当前未证明：真实外部服务持续可用、完整真实数据十步 Demo、两名真实用户效果、多用户安全、备份恢复、GraphRAG、多模态和最终垂类 SFT 生成质量。

### 4. 建议负责人角色

如果是单人开发，也要在清单中用角色区分工作，避免“所有事情都叫开发”：

- `产品/方案`：学科定位、用户、Demo 故事、PPT、商业化。
- `后端/AI`：模型、知识库、检索、Agent、权限、健康检查、可观测性。
- `前端/体验`：向导、状态、证据、失败恢复、AI 标识、可访问性。
- `评测/科研`：Gold、标准答案、人工评审、用户实验、效果报告。
- `交付/运维`：环境、迁移、数据快照、部署、备份、提交材料。

## 二、最终交付目标

在比赛提交前，至少形成下面 8 个可以独立审查的结果：

1. **一页产品定位**：明确学科、目标用户、三个核心任务、非目标和价值。
2. **一套权威资料快照**：有来源等级、许可、版本、更新时间和脱敏说明。
3. **一套冻结 Gold/效果评测集**：至少 12—20 个问题，至少 3 个典型问题有完整标准答案和证据。
4. **一份模型与技术实现说明**：解释基座模型、垂类组件、RAG、Agent 和回退策略各自作用。
5. **两名真实目标用户的效果报告**：有身份、任务、过程、指标、反馈和授权/脱敏记录。
6. **一个不超过三分钟的交互式 Demo**：从输入到输出完整展示，能解释实时步骤和冻结/缓存步骤。
7. **一套合规与安全材料**：伦理声明、AI 生成标识、数据分类、远程调用提示、权限和已知限制。
8. **一份可复现提交包**：代码、环境、迁移、数据清单、模型清单、启动手册、Smoke Test、许可证和版本校验。

## 三、总执行顺序与阶段放行

```text
T0 基线冻结
  ↓
P0-A 学科定位与用户任务冻结
  ↓
P0-B 权威资料、Gold 与质量证据冻结
  ↓
P0-C 真实用户验证与三分钟 Demo
  ↓
P0-D 合规、安全、可靠性和可复现提交包
  ↓
GATE-0 评委可验证版本
  ↓
P1 内容、体验、运维和商业化增强
  ↓
GATE-1 最终候选版本
  ↓
P2 技术先进性扩展（有余力再做）
```

### GATE-0：评委可验证版本

以下条件全部满足，才算 P0 完成：

- 评委在 60 秒内能说出目标学科、目标用户和核心痛点。
- 三个典型任务至少各有一条可演示路径。
- 至少 3 个典型问题具备标准答案、权威来源、系统回答和人工判定。
- 两名真实目标用户完成同一套结构化任务并留下效果证据。
- 三分钟 Demo 能从输入走到人工确认后的产物，并标明实时/缓存边界。
- AI 生成、未确认、证据不足、候选机会、静态代码检查等状态在 UI 和导出文件中明确可见。
- 公开演示具备最低访问控制；敏感资料不会未经确认发送给远程服务。
- 从干净环境或冻结环境可以按手册启动并通过 Smoke Test。
- README、Demo 脚本、迁移 head、测试数量、模型/数据版本和实际代码一致。

### GATE-1：最终候选版本

- P0 所有证据已进入提交包。
- 关键外部依赖有实时状态和离线 fallback。
- 关键页面无阻塞性 UI 错误，ESLint 无 error，P1 体验问题已完成取舍。
- 完成一次完整的候选版本回归，不再引入未经评测的核心链路变化。
- 所有比赛材料已通过一次“非开发者评审”：外部人员只看材料和 Demo，能够理解产品价值与限制。

## 十四、交付纪律

1. 每次开始工作前先执行 `git status --short`，确认没有覆盖用户已有修改。
2. 不使用 `git add .`、`git restore .` 或其他可能吞掉无关文件的命令。
3. 代码、文档、数据、部署和提交材料分开审查；不要把本机 `data/`、`storage/`、真实 key、真实用户材料直接加入提交包。
4. 每完成一个 P0 任务，立即保存验收证据：截图、日志、测试输出、报告、录屏或版本清单。
5. 核心链路进入 GATE-0 后，不再因为追求技术先进性随意替换模型、检索链路或数据快照。
6. 任何无法验证的能力都要写入“未验证/限制”，不能用自动化测试、Demo 截图或模型自评替代真实证据。
7. 本 Todo List 本身只负责规划；实际代码改动、提交和推送仍需按项目约定分别审查和授权。

# GapMind 赛题要求审查意见与修改建议

**审查日期**：2026-08-24
**审查分支**：`yx_dev`
**审查依据**：`docs/XH-202620_面向一流学科建设的学科垂类大模型与创新应用开发.pdf`、仓库现有代码/文档/评测材料、当前分支回归验证结果。
**审查性质**：只读审查；本文只给出意见和建议，不修改业务代码、不部署、不提交、不推送。

## 一、先给结论

GapMind 的工程底座已经比较完整：论文导入、解析、知识抽取、语义检索、Workspace Chat、Discover 多智能体、证据门禁、HITL 决策、研究计划、代码生成、研究空白棋盘、离线评测和前端工作台基本形成了可演示的研究闭环。当前分支回归验证结果也较好：后端 `469 passed`，前端 `56 passed`，TypeScript 检查和生产构建通过，ESLint 为 `0 errors / 14 warnings`。

但是，按照本次比赛的评分标准，项目当前最大的风险不是“功能页面不够多”，而是以下三件事尚未形成足够强的比赛证据：

1. **没有把产品明确收窄为一个“学科垂类大模型”的典型高校教学/科研场景**。目前的产品叙事更像“通用 AI/CS 科研工作台”，研究流程很强，但赛题要求的是明确学科、明确用户、明确痛点和明确效果。
2. **技术能力已有，验证材料还不够覆盖评分口径**。当前 Chat Gold 主要集中在 GNN 解释类问题，部分样本仍是 draft；测试通过不能替代权威标准答案、真实用户效果、外部服务可用性和完整演示证据。
3. **合规、公开部署安全和可复现提交包需要作为一等交付物补齐**。当前系统仍是单用户/MVP 认证模型，`X-User-ID` 可选且可伪造；部署说明也明确系统暂无登录。对本地单人演示问题不大，但对比赛提交材料、真实用户试用和公开地址会构成明显风险。

因此，建议把后续工作目标从“继续增加 Agent 或页面”调整为：

> **用一个足够聚焦的学科场景，把已有工程能力包装成可核验、可复现、可追溯、可证明有效的垂类科研助手。**

如果只剩有限时间，优先做垂直定位、真实用户验证、典型问题效果报告、合规安全、三分钟完整 Demo 和可复现提交包；混合检索、GraphRAG、更多 Agent 数量等应排在这些工作之后。

## 二、比赛要求与当前完成度对照

PDF 中明确要求系统面向具体一流学科及其真实教学/科研场景，核心功能至少包括：深度场景适配、自然语言交互、权威可信知识、内容可追溯；同时鼓励可复制扩展、多样化生成、复杂问题求解和个性化适配。评分项为：完成度 10 分、创意与实用性 20 分、技术实现 20 分、技术先进性 10 分、内容质量 20 分、商业化潜力 10 分、用户认可 10 分。

| 评分项 | 当前判断 | 已有优势 | 主要短板 | 建议目标 |
|---|---|---|---|---|
| 完成度 10 分 | **较好但未闭环证明** | 主流程和多个领域模块完整；测试覆盖较广 | 真实数据十步 Demo、提交材料、稳定性和外部依赖尚未形成一套可复核证据 | 冻结一个可复现 Demo 环境，完成完整输入—输出—人工确认闭环 |
| 创意与实用性 20 分 | **有亮点，场景仍偏宽** | Discover、Critic、证据门禁、HITL 和研究计划形成差异化闭环 | “为什么是某个学科的垂类系统”没有成为产品第一叙事 | 明确一个学科垂直切口、两类用户、三类高频任务和可量化收益 |
| 技术实现 20 分 | **强** | FastAPI/PostgreSQL/Milvus/Celery、证据回链、多 Agent、来源隔离、离线评测 | 权威知识库、模型训练/微调证据、多模态和专业计算组件的比赛证明不足 | 增加知识源治理、模型卡、组件版本、专业计算或数据分析最小闭环 |
| 技术先进性 10 分 | **部分满足** | 证据护照、引用质量门禁、失败分类、人工确认边界较成熟 | 当前 Chat 是向量检索+重排，生产路径未实现混合检索/GraphRAG；多模态和垂类 SFT 证据不充分 | 选一个能实际演示并测量的先进点，不要只在方案中罗列技术名词 |
| 内容质量 20 分 | **工程机制好，外部证明不足** | Fail-closed、来源标记 `[En]/[Pn]/[Dn]/[Cn]`、Citation Quality Gate、Gold/人工 verdict | 评测样本集中于 GNN；部分 Gold 为 draft；没有完整的三类典型问题标准答案、权威来源和用户效果报告 | 建立冻结版典型问题集，逐题给出标准答案、来源、人工判定和错误分析 |
| 商业化 10 分 | **偏弱** | 工作台形态有机构复用潜力 | 单用户、无权限/租户/配额；部署和数据版权/授权说明不完整 | 提供高校试点方案、部署形态、成本估算、数据授权策略和扩展边界 |
| 用户认可 10 分 | **尚未证明** | 产品已有教学/学生/研究者可使用的功能雏形 | 尚未看到至少两名真实目标用户的身份、频率、场景、效果和原始反馈证据 | 至少完成两名真实用户的结构化试用，形成可核验效果报告 |

### 对 PDF 核心功能的逐项判断

- **深度场景适配**：当前“科研工作台”能力完整，但学科和岗位场景没有足够显式。需要从首页、Workspace 创建、Chat 提示词、Demo 和效果报告中统一体现一个垂直学科。
- **自然交互**：Workspace Chat 已支持多轮、流式输出、上下文选项、失败提示和来源引用；仍需提升歧义澄清、任务边界提示、长任务进度和用户角色适配。
- **权威可信知识**：当前论文、知识项、Semantic Scholar 和向量检索基础较好，但尚需构建权威等级、版本、新鲜度、许可、人工审核状态，不能仅以“检索到了论文”代表权威知识库。
- **可追溯内容**：这是项目的明显强项。建议继续强化页码/段落/高亮、来源层级、时间和生成版本的展示，并把追溯能力贯穿报告、计划、代码草稿和外部核验结果。
- **可复制扩展**：领域模块和端口抽象具备基础，但当前仍受本地存储、外部模型、单用户部署和未锁定依赖约束，需要通过部署包和数据种子证明可复制。
- **多样化生成**：已有研究计划、代码、分析、写作、审稿回复等 Agent 类型，但必须持续显示 AI 草稿、未验证、证据范围和人工确认状态。
- **复杂问题求解**：Discover 的 Planner → Evidence → External Novelty → Opportunity → Critic → Gate 是项目最适合比赛展示的复杂工作流，应重点做可视化和分支解释。
- **个性化适配**：目前 Workspace 只有主题、关键词、目标、约束和问题，缺少用户身份、知识水平、研究偏好、历史使用和可撤销的个性化配置，建议列为高优先级体验补强项。

## 三、最重要的 P0 建议：建议判定标准前必须完成

### P0-1：把产品从“通用科研工作台”收窄为一个明确垂直场景

#### 问题判断

README 和整体导航强调的是“Human-in-the-Loop AI Research Workspace”，这对于产品架构是合理的，但对于本次比赛会产生一个问题：评委可能看到了很多技术模块，却不容易在一分钟内回答“这到底服务哪个一流学科的什么核心痛点”。

结合现有 GNN 评测、知识图谱、研究空白和 Discover 设计，建议优先考虑以下叙事方向之一：

> **计算机科学—图机器学习/图神经网络科研创新助手**：面向研究生、导师和科研团队，解决文献理解、研究空白识别、外部新颖性核验、可证伪计划生成和代码起草问题。

也可以选择团队更有真实数据和用户基础的其他学科，但必须做单一主切口，不能在 Demo 中同时宣称服务所有学科。

#### 建议修改

1. 在首页和 Workspace 创建向导中明确“学科—用户—任务”三元组，而不是只填写主题和关键词。
2. 给出一个清晰的非目标范围，例如“不替代导师判断、不提供未经证据支持的学术结论、不自动执行生成代码”。
3. 将现有 10 步 Demo 改成一个真实任务故事：用户是谁、带着什么问题进入、系统用哪些证据完成什么决策、用户在哪一步确认、最后节省了什么时间或减少了什么风险。
4. 为教师/导师、研究生、科研助理分别设置默认输出模板、解释深度和允许的自动化程度。
5. 用 3 个典型任务承载产品叙事：
   - 文献与概念问答：必须有权威来源和页码/段落证据；
   - 研究机会核验：必须区分支持证据、反证、外部新颖性和未确认假设；
   - 研究计划/代码草稿：必须有可证伪性、数据集、基线、指标、风险和人工确认。

#### 验收标准

- 评委只看首页、Chat 和一次 Demo，能说出目标学科、目标用户和核心痛点。
- 所有页面、提示词、评测 Gold、Demo 话术和效果报告中的学科名称一致。
- 至少有两名该场景真实用户愿意按同一任务流程试用并给出反馈。
- 对不属于目标学科或目标任务的问题，系统能明确提示“当前知识范围/能力范围”，而不是泛化回答。

### P0-2：证明“垂类大模型/垂类智能能力”，不要只展示通用模型加 RAG

#### 问题判断

当前配置和代码显示，主生成能力依赖 Deepseek，向量与重排依赖 BGE 系列；Gap Board 使用的 `research-dataset-qwen3`/Ollama 属于特定抽取路径。工程上这样组合是合理的，但比赛要求是学科垂类大模型与创新应用，评委会追问：垂类能力到底来自哪里？是微调模型、知识库、工作流，还是仅仅是提示词？

#### 建议修改

补充一份可审计的模型卡和对照实验，不一定要求重新训练大模型，但必须准确说明各组件职责：

| 组件 | 需要说明的内容 |
|---|---|
| 生成模型 | 服务 ID、模型版本、上下文长度、温度/采样设置、是否启用思考、备用模型及切换条件 |
| 垂类模型或抽取模型 | 训练/微调目的、数据来源、脱敏方式、LoRA/SFT 配置、版本、推理位置、失败回退策略 |
| 知识库 | 学科范围、来源类型、版本、权威等级、许可、更新时间、人工审核状态 |
| 检索与排序 | embedding、Milvus、reranker、召回数量、去重与纸级多样性策略、失败时的安全行为 |
| Agent 工作流 | 每个角色的输入输出、分支条件、人工确认点、是否可重试、是否会产生持久化资产 |

至少提供以下 A/B 结果：

1. 通用模型无领域上下文；
2. 通用模型 + 学科知识库/RAG；
3. 垂类抽取/微调组件 + RAG + 工作流。

比较事实准确性、引用有效性、任务完成率、拒答/不确定性质量、延迟和人工修改量。若目前没有一个用于最终生成的垂类 SFT 模型，应在方案中诚实表述为“垂类知识增强与垂类抽取组件”，不要把普通基座模型包装成已经完成的垂类大模型。

#### 验收标准

- 评委可以看到一个版本化的模型卡和对照表，而不需要从代码猜测垂类能力来源。
- 至少 3 个目标学科问题在“无知识库”和“有知识库/垂类组件”之间有可解释的改进。
- 所有线上输出都能标明使用的模型/服务版本、知识库快照和提示词/Schema 版本。

### P0-3：把内容质量从“测试通过”提升为“典型问题可证明正确”

#### 已有基础

`evaluation/chat/` 已经具备离线评测协议、来源标记检查、grounded 判断和人工 verdict 边界；`gnn_explanations_gold_v1/v2` 及 v3 draft 为后续建立 Gold 奠定了基础。当前 Chat 服务也具备 fail-closed、引用一致性检查、来源护照和有限修复机制。

#### 主要缺口

- 现有 Gold 主要围绕 GNN 解释类问题，不能代表整个研究助手的内容质量。
- 部分样本仍是 draft，不能作为生产阈值或最终比赛证据。
- 机械上“有引用”不等于事实正确；当前文档也已明确这一点。
- 还没有把 PDF 要求的“至少 3 个典型问题、标准答案、来源证据、准确性证明”组织成评委一眼能看懂的报告。

#### 建议建立冻结版质量集

建议至少包含 12—20 个问题，覆盖以下类别，每题均有标准答案、允许的表述差异、必需来源、禁止过度推断和人工判定：

1. **基础知识/概念规范题**：术语定义、方法假设、公式变量含义；
2. **跨论文比较题**：方法差异、实验设置、适用边界；
3. **证据不足题**：材料不足时必须拒绝绝对结论；
4. **研究设计题**：数据集、基线、指标、消融、统计检验和潜在偏差；
5. **新颖性/反证题**：支持证据、相似工作、反证和未验证候选必须分栏；
6. **面向不同用户的解释题**：本科生/研究生/导师需要不同深度，但不能改变事实。

每题记录：问题、用户角色、输入资料快照、标准答案、权威来源、必要引用、系统回答、citation precision/recall、grounded、人工正确性、是否需要修改、失败原因和修复版本。Gold 冻结后不得用产品结果反向改标准答案。

#### 验收标准

- 至少 3 个典型问题可在 3 分钟内现场展示完整证据链。
- 所有“正确”结论均能回到真实来源；无来源时系统会明确说证据不足。
- 报告将机械指标、人工正确性、真实用户满意度分开，不能用单一分数代替质量。

### P0-4：完成两名真实目标用户验证和三分钟可交付 Demo

PDF 明确要求效果验证报告至少包含两名真实目标用户，并要求视频不超过三分钟、必须是交互式完整输入—输出过程，不能只是 PPT 或配音。

#### 建议的用户验证记录

至少选择两名真实目标用户，最好覆盖“研究生/科研助理”和“导师/教师”两种角色。每人记录：

- 身份与学科背景；
- 使用频率或试用次数；
- 实际任务和输入资料；
- 从导入、检索、问答、Discover、人工确认到计划/代码草稿的完成情况；
- 节省时间、减少重复劳动、发现反证或降低误判的具体例子；
- 用户主动指出的错误、卡点和不信任点；
- 用户是否愿意继续使用，以及需要什么权限/数据/模型保障。

不要只收集“很好用”的主观评价，应记录任务前后时间、完成率、人工修改次数、引用核查耗时、错误召回情况等可比较数据。涉及论文、学生信息、实验数据时必须去标识化并保留授权说明。

#### 三分钟 Demo 建议结构

1. 0:00—0:20：一句话说明学科、用户和痛点；
2. 0:20—0:45：导入或选择已冻结的脱敏资料，展示解析/索引状态；
3. 0:45—1:20：提出一个典型问题，展示多轮回答、引用、页码/证据和证据不足时的拒答；
4. 1:20—2:20：启动 Discover，展示 Planner、Evidence、External、Critic、Gate 分支和支持/反证证据；
5. 2:20—2:50：人工确认一个候选，生成计划或代码草稿，明确显示 AI 草稿/静态检查/未执行；
6. 2:50—3:00：展示效果数字、风险边界和下一步人工判断。

视频应准备离线可重放的冻结资料、模型快照或缓存结果，并在视频或说明中标注哪些步骤是实时调用、哪些步骤来自预置快照，避免因 S2、Ollama、LLM 或网络波动导致现场失败。

### P0-5：在真实用户前补齐认证、数据隔离和合规边界

#### 已发现的风险

- `backend/app/core/deps.py:32-42` 中当前用户通过可选的 `X-User-ID` 获取，默认值为 `user`，代码注释也说明是 MVP 单用户模型。
- `backend/app/domains/chat/models.py` 说明会话按部署范围存在，不是按用户隔离。
- `deploy/README.md` 明确写有系统暂无登录，公开部署需要另外启用基础认证；安全检查清单仍未完成。
- `main.py` 的 CORS 配置允许凭据，并使用宽泛的 methods/headers；配置默认 `APP_HOST=0.0.0.0`。
- PDF 上传接口目前先读取文件再做大小判断，主要按扩展名校验；本地文件存储不等于有权限、配额、病毒扫描或生命周期管理。

这并不影响本地单人开发，但会影响真实用户试用、评委访问地址以及“伦理与安全合规性声明”。

#### 建议修改

1. 比赛演示至少加一层明确的访问控制，并确保所有 workspace、paper、artifact、chat、agent、download/view API 都经过同一套 workspace ACL；不能只保护部分领域路由。
2. 增加数据分类与上传提示：公开、内部、敏感、不可上传；未经脱敏的学生信息、患者数据、案例数据不能发往远程模型或第三方 API。
3. 增加 PII/敏感信息检测、远程调用前确认、日志脱敏、留存期限、删除/导出流程和外部服务位置说明。
4. 所有 AI 生成内容在 UI、导出报告和视频中保留“AI 生成内容/未经人工确认”标记；确认后的研究计划也保留生成版本和确认人。
5. 把学术诚信边界写入产品：不得伪造文献、实验结果、引用、用户反馈或人类结论；证据不足时必须保留未确认状态。
6. 生产配置禁止弱密码和默认密钥，CORS 改为明确的允许域名，健康检查不能把“API key 存在”当成服务可用。

#### 验收标准

- 未登录或无权限用户无法读取其他用户/Workspace 的论文、聊天、产物和下载接口。
- 远程 fallback 前能显示数据将发送给哪个服务，敏感资料默认不发送。
- `/health/ready` 能分别报告 DB、Redis、Milvus、LLM/Embedding、队列等依赖状态；依赖不可用时返回非就绪，而不是始终 `status=ok`。
- 合规声明、产品 UI、导出文件和 Demo 话术对 AI 标识、数据处理和人工确认边界一致。

### P0-6：制作可复现、可审查的提交包，清理文档和产品入口不一致

#### 当前问题

1. `README.md` 引用了 `docs/fine_tuned_gap_board_integration.md`，仓库中未发现该文件；`docs/0811_demo_script.md` 还引用了未发现的 `docs/0809_freeze_version.md` 和 `docs/0811_e2e_results.md`。

3. 本地 `data/`、`storage/` 和部署物料没有形成可供评委复现的最小脱敏数据包；不能依赖开发机上的用户语料作为唯一 Demo 资产。
4. 根目录有一个未纳入正常产品导航的 `index.html`，内容和品牌更接近独立的 “GraphRAG-X” 原型，可能造成评委打开入口后看到与 GapMind 主产品不一致的页面。
5. 前端有 `package-lock.json`，但后端没有等价的 Python 依赖锁定文件；仓库没有发现 CI 配置。

## 四、分模块审查与具体建议

### 4.1 知识库与证据治理

#### 优点

- 论文、知识项、关系、证据片段、抽取运行和拒绝记录的领域拆分较完整。
- Chat 已经严格区分论文 `[En]`、研究计划 `[Pn]`、报告 `[Dn]`、代码草稿 `[Cn]`，并在引用失效时告警或 fail closed。
- Discover 有 Evidence Passport、独立论文数、全文/元数据、证据门和人工状态等概念，符合科研助手“证据先于结论”的定位。

#### 建议

1. 为每个知识源增加权威等级：教材/标准/官方数据库/同行评审论文/预印本/用户上传资料/模型生成草稿。
2. 增加 DOI、出版物、版本、发布日期、修订日期、来源 URL、许可、获取方式、页码和文本哈希；论文更新后旧快照不可静默覆盖。
3. 增加知识项人工审核状态和审核记录，明确“抽取事实”“模型归纳”“用户假设”三类对象。
4. 为过期或争议来源提供新鲜度提醒；回答中展示证据时间，尤其是技术标准、软件版本和前沿研究。
5. 将上传 PDF 的解析质量指标纳入状态：页数、文本覆盖率、公式/表格/图片提取率、乱码率、失败页和可检索页数。
6. 当前章节分布显示 `Unknown` 占比较高、Method/Experiment/Related Work 覆盖稀疏。应先提升章节识别和元数据质量，再决定是否上线章节加权或图检索。
7. 补充版权与数据授权台账。比赛中展示“权威知识库”时，必须能回答资料从哪里来、是否允许处理、是否允许向外部模型发送。

### 4.2 Workspace Chat 与 RAG

#### 优点

- 同步和 SSE 路径都使用 `disable_thinking=True`，对生成预算和延迟做了约束。
- 有最新历史保留、按论文去重、上下文字符预算、检索失败分类、无证据时拒答和有界引用修复。
- 生成阶段不会通过修复器凭空增加新引用，能够维持来源护照边界。
- 评测工具坚持“机械通过不等于事实正确”，这是比赛内容质量证明中应保留的严谨性。

#### 建议

1. 在 Chat 首屏明确当前检索范围、当前资料快照、是否包含研究计划/报告/代码草稿，以及不在范围内的内容。
2. 把“资料问答”和“启动研究操作”视觉上分开。意图建议可以存在，但 AgentRun、Task 或长期资产必须由用户显式确认。
3. 引用卡片增加页码、段落、原文高亮、来源等级、发布日期、文件版本和“支持/反证/背景”标签。
4. 对以下状态给出不同用户动作：无命中、检索服务失败、外部服务超时、来源过期、引用修复失败、证据不足。不要都归纳为“回答失败”。
5. 评测增加问题级别的 answerability：资料中没有答案时，正确行为是拒答或提出补充材料请求，而不是以“回答完整度”作为唯一指标。
6. 当前生产 Chat 是 dense retrieval + reranker，尚未实现混合检索或 GraphRAG。方案、演示和评审材料中不要把“有知识关系表/知识图谱页面”写成“Chat 已经使用 GraphRAG”。如果后续要做，应先建立独立 A/B 集，再决定是否上线。
7. 当前实验章节数据较稀疏，facet 检索也有回归样本，建议将实验特性明确标为 opt-in/beta，避免把实验结果当成生产承诺。

### 4.3 Discover 多智能体与复杂问题求解

#### 优点

Discover 是最有比赛展示价值的模块。Planner、Evidence、External Novelty、Opportunity、Critic、收窄补查、Gate 和 HITL 决策形成了真实的多步骤研究流程，不是简单地并列几个 Agent 名称。证据门要求至少两篇独立全文支持，并区分 `confirmable`、`verified`、`needs_more_evidence`，方向正确。

#### 建议

1. 把工作流画成一张状态图，标出每一条正常、部分成功、可重试、需人工、不可继续的分支。
2. 在 UI 中展示每个 Agent 的输入、输出、证据、耗时、重试次数、模型版本和失败原因；当前已有 AgentStep 观测基础，应把它转化为评委可理解的解释。
3. 对 S2 查询和精确查找明确配额、缓存、退避、部分成功规则和最终结论降级规则。外部核验失败时，不要显示为“已完成的新颖性判断”。
4. 对 Critic 的 `keep/narrow/reject` 给出可读的证据理由和下一步动作，避免用户只看到一个标签。
5. 将“候选研究机会”“已验证研究机会”“人工确认机会”严格分层，导出报告中不要把候选写成事实。
6. 给每次 Run 增加幂等键、可恢复 checkpoint、取消后清理规则和成本摘要，防止网络重试产生重复候选或重复外部调用。
7. Demo 时优先演示一条有真实分支的 Run，而不是只展示成功路径；例如“支持论文不足 → Critic narrow → 补查 → 仍需人工确认”。

### 4.4 Agent 产物、研究计划和代码生成

#### 已有边界值得保留

- 研究计划/深度研究有等待用户确认的门禁。
- 代码生成前端明确写出“静态检查/计划覆盖，不代表代码已经执行”。
- 生成文件会做路径和大小限制，避免生成物直接越界写入。

#### 建议

1. Analyze/Write/Respond 等 W7 产物也统一显示“AI 生成、未人工确认、未必有论文证据”，并提供审阅、接受、驳回、修订、版本比较，而不是只标为 candidate。
2. 研究计划中的数据集、基线、指标、统计检验和默认公式都应注明来源：来自用户输入、论文证据、模板建议还是模型推断。
3. 研究计划确认后，保留确认人、确认时间、输入资料快照和可追溯版本；资料更新后标记计划可能过时。
4. 代码生成结果至少提供依赖清单、入口文件、测试文件、运行命令、预期输出和许可证风险；静态完整性检查与真正运行验证分开表述。
5. 若未来增加沙箱执行，必须是用户显式触发、资源隔离、网络默认关闭、超时/内存限制、依赖白名单和完整日志；在此之前，材料中不要声称“自动验证研究代码”。
6. 对导出的报告、计划、代码 ZIP 嵌入机器可读的 provenance manifest，包含来源 ID、证据快照、生成模型、提示词/Schema 版本和人工状态。

### 4.5 多模态、专业计算和研究数据分析

PDF 把文本/图片/表格解析与生成、专业计算和数据分析列为技术建议。当前项目的强项仍是 PDF 文本、知识抽取和文献证据链，不能默认等同于已经具备多模态科研能力。

建议按“最小可证明闭环”取舍，不要一次扩展过大：

1. PDF 图片/表格：对图表做区域识别、标题/图例/轴信息提取，并将结果关联回页码和原图；无法可靠解析时显式标记。
2. CSV/XLSX：允许用户上传小型研究数据，展示字段预览、缺失值、类型、统计摘要和数据质量警告；不得把原始敏感数据自动发送给远程模型。
3. 专业计算：先选择一个目标学科最常用的可复现计算，例如指标计算、显著性检验、消融表对比或公式检查，结果由确定性代码产生，LLM 只负责解释。
4. 图像/OCR：若没有可靠模型和证据回链，宁可标记为后续范围，也不要在方案中泛称“支持多模态”。
5. 用一个端到端样例证明“上传数据—分析—可视化/表格—文字解释—来源/公式/脚本回链”，这比增加一个孤立的上传按钮更有价值。

### 4.6 前端产品体验

#### 当前体验优点

- 全局导航已覆盖首页、Workspace、论文检索、AI 助手、阅读和研究资产。
- Chat Composer 能选择直接问答、研究计划、代码、分析、写作、审稿回复等模式，并提供显式上下文选项。
- Discover 已有运行进度、查询日志、AgentStep、部分成功提示、Opportunity Panel、Evidence Passport 和人工决策界面。
- 独立模式被明确标记为“不检索”，这是避免用户误以为回答来自论文的好设计。

#### 建议按用户旅程重做体验重点

**首次进入**：提供“选择学科/角色/目标/资料敏感级别”的 60 秒向导，并展示系统能做什么、不能做什么。不要让用户先理解十几个页面和 Agent 名称。

**资料导入**：做成向导式流程，显示文件类型/大小/页数校验、解析进度、可检索页数、失败页、Embedding 状态、权限和数据处理去向。批量导入不能只显示一个最终数量。

**问答**：把问题、证据、回答、下一步行动分成三个层级；引用支持页码和高亮；无证据时提供“上传资料/缩小问题/查看失败原因”，而不是只让用户重试。

**研究发现**：把每个候选的“为什么出现、支持什么、反对什么、还缺什么、下一步查什么”固定成卡片；Gate 不通过时也要能继续人工编辑，而不是让用户猜测系统状态。

**产物审阅**：所有计划、报告、代码和回答都应有状态色彩和文字说明：草稿、待审核、已确认、已驳回、证据过期、生成失败。状态名称应在全产品统一。

**失败恢复**：针对解析失败、检索故障、外部查询部分成功、模型超时、引用质量不达标、Gap 标注校验失败分别给出原因、可重试动作和是否会产生费用。

**可访问性和性能**：修复当前 14 个 ESLint 警告，检查键盘操作、焦点管理、颜色对比、长文本阅读和窄屏布局；生产构建的主 JS 包约 1.83MB，建议对图谱、Discover、阅读器和 KaTeX 等做更细的动态分包。

### 4.7 部署、可靠性、可观测性和工程交付

1. `health/ready` 应做真正的依赖级健康检查，并区分 liveness/readiness；启动时检查 migration head、存储目录、队列和模型服务。
2. 为 Postgres、Redis、Milvus、MinIO、Celery worker、LLM、Embedding、Reranker、Semantic Scholar 分别给出故障处理和用户可见降级。
3. 增加一条无外部服务的离线 Demo 模式：使用冻结知识库和缓存结果，仍保留来源、版本和“非实时”标记。
4. Chat 已有 retrieval/generation audit，建议扩展到一次完整用户任务：trace ID、Workspace、模型/知识快照、耗时、token/费用、重试、失败分类、人工确认和最终导出。
5. 日志不得记录 API key、原始敏感资料或不必要的完整 prompt；导出审查日志时提供脱敏版。
6. 增加 CI：后端测试、前端测试、TypeScript、构建、lint、迁移检查、OpenAPI 生成差异检查、文档链接检查和最小启动 smoke test。
7. 增加 Python 依赖锁定或可重建环境方案，并固定 Node、Python、数据库、Milvus 和模型服务版本；不要只依赖开发机当前虚拟环境。
8. 增加迁移和备份恢复演练。`alembic check`、从空库启动、从冻结快照恢复和升级/回滚都应进入发布前检查。
9. 维护一份“实时服务状态表”：最后验证时间、服务地址、模型版本、配额、是否可用于 Demo。测试 mock 通过不代表外部服务当天可用。

### 4.8 商业化与复制推广

比赛的商业化 10 分不能只靠“可以部署”。建议把产品包装成可落地的高校试点方案：

- **首个客户**：某一学院/实验室/研究生课程组；
- **首个场景**：文献阅读与研究机会发现，或研究方法课程辅助；
- **输入资产**：学校授权教材、课程资料、论文库、实验数据规范；
- **交付形态**：校内部署、私有化部署或受控云服务；
- **成本模型**：基础设施、向量存储、模型调用、外部检索、运维和人工审核成本；
- **扩展方式**：新增学科时替换知识源、评测集、模板和垂类抽取器，而不是复制全部代码；
- **风险边界**：学术诚信、资料版权、数据跨境/第三方处理、用户权限和模型供应商锁定。

最好准备一个小规模压测或容量估算：例如 2 名用户同时导入、若干并发 Chat、一次 Discover 的平均耗时和费用，外加缓存命中、队列等待和外部服务限流后的体验。没有多租户能力时，应明确将当前版本定位为“院系/实验室单租户试点”，不要直接宣称可支持大规模高校用户。

## 五、建议的产品主流程

推荐把 Demo 和产品首页统一为下面这条链路，降低评委的理解成本：

```text
选择学科与角色
      ↓
建立受控 Workspace：范围、资料许可、敏感级别、研究目标
      ↓
导入权威资料：解析质量、来源等级、版本和可检索状态
      ↓
资料问答：多轮澄清 + 证据引用 + 无证据时拒答
      ↓
研究发现：支持证据 + 反证 + 外部新颖性 + Critic 收窄
      ↓
人工确认：候选不是事实，确认记录不可变
      ↓
计划/代码/分析草稿：生成版本、来源、风险和静态检查
      ↓
导出可复现包：证据清单、模型清单、数据版本、人工确认和限制
```

每一步都应有一个评委能看懂的结果指标：

| 环节 | 建议指标 |
|---|---|
| 导入 | 解析成功率、可检索页覆盖率、失败页率、索引耗时 |
| 问答 | 人工事实正确率、引用 precision/recall、无证据拒答准确率、P50/P95 延迟 |
| 发现 | 证据门通过率、独立全文数、反证覆盖率、外部检索部分成功率 |
| 计划 | 人工一次通过率、必需字段完整率、证据覆盖率、修改次数 |
| 代码/分析 | 静态检查通过率、依赖/入口/测试完整率、人工可运行率（如未执行则明确不统计） |
| 用户 | 任务完成时间、重复检索时间、人工核查时间、继续使用意愿 |

## 六、建议的优先级与实施顺序

### 第一阶段：评委可验证的 P0（建议立即完成）

1. 冻结一个学科垂直定位、两类用户和三个核心任务。
2. 冻结 12—20 个带标准答案与权威证据的问题集，至少覆盖 PDF 要求的三个典型问题。

## 九、最终建议

GapMind 不需要再用“增加几个 Agent”来证明复杂度；它已经有足够强的工程复杂度。下一步最值得投入的是把复杂度转换为评委可理解的价值和证据：

1. 用一个明确学科和真实用户讲清楚为什么必须做这个系统；
2. 用权威知识、证据护照和 fail-closed 证明系统不会把猜测伪装成事实；
3. 用三类典型问题、两名真实用户和一个三分钟完整 Demo 证明它真的有效；
4. 用合规、安全、版本、数据许可和可复现提交包证明它可以被学校或实验室放心试用；
5. 对尚未完成的 GraphRAG、多模态、代码执行和大规模商业化保持准确边界，避免过度承诺反而损失可信度。

以当前代码基础，项目具备冲击“技术实现”和“复杂科研流程”相关评分的条件；能否进一步拿到“内容质量、用户认可、商业化和技术先进性”的分数，关键取决于上述证据与交付材料，而不是继续扩展功能数量。

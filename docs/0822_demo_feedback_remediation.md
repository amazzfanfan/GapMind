# 全流程预演反馈：问题归因与收尾方案（2026-08-22）

## 目标与决策

本轮预演暴露的不是主链路缺失，而是几个会让用户误解系统边界、可靠性或产物成熟度的体验缺口。收尾原则如下：

- 证据检索失败时宁可明确失败，也不生成伪造的工作区事实。
- AI 生成的计划、代码和棋盘标注仍然是候选，保留来源、版本和人工确认边界。
- 不让用户承担不必要的“先选对功能才能提问”的认知负担。
- 不把单个非关键上游失败渲染成整条 Discover 链路失败，但审计信息必须保留。

## 优先级

| 优先级 | 编号 | 事项 | 原因 |
|---|---|---|---|
| P0 | D1 | 助手的计划感知问答与上下文解耦 | 当前直接阻断“此计划相对 ProtGNN 的贡献/损失函数”等核心讲解问题。 |
| P0 | D2 | 工作区检索故障可诊断与可恢复 | 当前提示将 embedding、Milvus、reranker 等根因混为一谈，无法快速恢复演示。 |
| P0 | D3 | 代码生成检查分层与一次候选修复 | 当前“静态检查”容易被误解为完整运行验证，也未形成诊断后的修复闭环。 |
| P1 | D4 | Discover 外部检索部分成功分级呈现 | 11/12 成功不应以全局警告压过已获得的外部证据。 |
| P1 | D5 | Gap 标注远程备份抽取器 | 提升小模型或隧道不可用时的完成率，但涉及远程材料传输、凭据与成本。 |

## D1：助手上下文与工作流操作解耦

### 现象与根因

“资料问答”只把工作区论文检索结果送入 RAG；研究计划不是论文语料，且问答模式没有计划选择器。因此“此研究计划相对 ProtGNN 的核心贡献和损失函数”无法解析“此计划”。

### 决策

不采用“完全自动识别并自动启动 Agent”。改为“默认智能问答 + 显式上下文 + 仅建议的意图路由”：问答可自动选择资料来源；任何会创建 AgentRun、任务或长期产物的操作仍由用户确认。

### 实施方案

1. 主输入框默认是“提问”，将并列的 Agent 模式收进“更多研究操作”。
2. 在输入框上方增加 Context chips：工作区论文、当前研究计划、已确认深度研究报告、代码草案（后两者可选）。
3. 从研究计划、深度研究、代码生成页面进入助手时，以 `research_plan_id` 自动预选；用户仍可切换或清除。
4. 问答 API 接收经校验的 `research_plan_id`，只允许访问当前 workspace 的已确认计划；后端将计划快照与论文检索证据同时加入上下文。
5. 每条回答保存来源清单，而不是将计划伪装为论文 Evidence：`[P1] 已确认研究计划`、`[E1] 工作区论文`、`[D1] 已确认报告`、`[C1] 代码草案，未运行验证`。
6. 若“此计划”存在歧义，展示最多 3 个候选计划供选择；不猜测。若计划未定义损失函数，明确说明缺失及可查看的草案来源。
7. 意图路由仅在检测到“生成代码、写作、分析结果、回应审稿意见”等操作性表达时显示建议卡；用户点击后才启动 Agent。

### 验收

- 在已选择计划的问答中，能区分计划贡献与 ProtGNN 论文证据，并分别标源。
- 多计划时不误绑定；跨 workspace 计划被拒绝。
- 自动意图建议不会自行创建任务、研究计划或代码产物。
- 普通论文问答继续保持现有 grounded `[En]` 一致性检查。

### D1 实施记录（2026-08-22）

- 普通助手入口默认是“直接提问”；“生成研究计划、代码生成、结果分析、论文写作、审稿回复”收进“更多研究操作”。操作模式只产生启动建议，用户二次确认后才调用 Agent API，因此不会因问题措辞自动创建 AgentRun、Task 或长期产物。
- 新增工作区上下文选项接口。只返回当前 workspace 内可确认追溯的研究计划，以及绑定同一计划的已确认深度研究报告和代码草案。跨 workspace 的 `research_plan_id` 或补充产物 ID 会被拒绝，多计划下的“此研究计划”不会猜测绑定。
- 普通 chat 请求接收并校验 `research_plan_id`、`source_artifact_ids`。回答上下文同时包含研究计划快照、工作区论文检索证据和用户选择的补充产物；计划没有独立损失函数时，提示词明确要求回答“计划未提供”，不得从论文或常见做法补写。
- `chat_messages.source_manifest` 通过 Alembic `0019_chat_message_sources` 持久化来源快照。论文仍保存在 `chat_message_evidence` 并使用 `[En]`，计划、报告、代码草案分别使用 `[P]`、`[D]`、`[C]`，前端来源面板明确显示“代码草案，未运行验证”。
- 验收测试覆盖单计划分源、多个计划歧义、跨 workspace 拒绝、报告/代码补充来源、来源 marker 校验及前端来源面板。当前验证：后端 `421 passed`，前端 `53 passed`，TypeScript 类型检查和生产构建通过。

## D2：工作区检索失败的诊断与恢复

### 现象与根因

`semantic_search` 会串联 SiliconFlow embedding、Milvus 和 reranker；任一异常都被归为 `retrieval_failed`。无命中不是该错误，而是正常的“证据不足”分支。

### 实施方案

1. 在检索层把失败归类为 `embedding_unavailable`、`milvus_unavailable`、`collection_unloaded`、`reranker_degraded` 和未知错误，并保留安全诊断码。
2. 前端根据诊断码显示对应恢复动作：检查 API Key/Windows 环境变量、检查基础设施、重新加载 collection，或在 reranker 故障时降级为向量结果。
3. 在课题助手发送前进行轻量检索健康提示，不阻断普通独立对话。
4. 失败后提供“重试检索”；不能恢复时允许用户明确切换为不使用工作区证据的通用对话，回答显著标记为无论文回链。
5. 仅在 Milvus 数据丢失或文献未向量化时提示重建索引，不能把所有失败都指向重建。

### 验收

- 模拟 embedding、Milvus、reranker 失败分别显示可操作的中文提示。
- 无向量命中不会被报告为服务故障。
- 工作区事实问答在检索失败时仍然 fail closed，不产生无依据断言。

### D2 实施记录（2026-08-23）

- 检索响应新增安全 `diagnostic_code`：`embedding_unavailable`、`milvus_unavailable`、`collection_unloaded`、`reranker_degraded`、`unknown`。原始上游异常只写后端日志，不进入工作区 API 文案；collection 未加载单独提示重新加载，不把所有问题指向重建索引。
- `semantic_search`、similar work 和 counter evidence 都保留失败/空结果边界。reranker 异常继续回退到向量分数，但响应状态变为 `degraded` 并携带 `reranker_degraded`；Milvus 返回零命中仍是正常成功结果，不转成故障。
- workspace Chat 在检索失败时把安全诊断码持久化到 `chat_messages.retrieval_diagnostic_code`（Alembic `0020_chat_retrieval_diagnostic`），回答不调用 LLM，流式请求结束为可重试的失败状态；降级结果仍可回答但前端显示对应恢复动作。现有失败消息的“重新尝试”入口继续作为重试检索入口。
- 前端按诊断码区分 embedding Key/地址、Milvus 基础设施、collection 加载和 reranker 降级提示；未知故障不展示原始异常。未命中仍展示“没有使用工作区证据”，不伪造论文事实。
- 验收测试覆盖 embedding、Milvus、collection、reranker、普通零命中、流式 fail-closed 与前端诊断文案。当前验证：后端 `422 passed`，前端 `53 passed`，TypeScript 类型检查和生产构建通过；Alembic 已升级到 `0020_chat_retrieval_diagnostic`。

## D3：代码生成的检查语义与候选修复

### 现象与根因

现有“静态检查”是交付完整性检查：蓝图文件、Python AST、入口、测试、README/requirements 和依赖声明。它不是运行验证；另有“计划覆盖度自检”用于呈现研究计划的缺口。

### 决策

保留检查，不自动执行生成项目，也不承诺一次生成即可运行。

### 实施方案

1. UI 改名为“交付完整性检查”，分为阻断项（缺文件、语法、入口）与改进项（测试、README、依赖声明）。
2. 将“计划覆盖度自检”作为独立区域，明确它不代表程序已验证。
3. 蓝图默认要求 README、requirements、配置、最小测试、固定随机种子和评估入口。
4. 增加最多一次“诊断驱动修复”：把失败检查及相关文件交给模型生成修订候选，再运行同一检查，展示差异和前后结果。
5. 未来如需真实验证，单列用户主动发起的“受限验证”：临时、无网络环境中运行 `compileall` 与指定测试；不恢复已移除的自动执行路径。

### 验收

- 用户能看懂每条检查是阻断还是建议，不会把 5/6 当成“项目运行失败”。
- 修复循环最多一次，始终只产生可预览候选，不覆盖已有产物。
- 下载包中具备项目说明、依赖、配置和最小测试骨架。

## D4：Discover 外部检索部分成功的分级

### 现象与根因

外部检索最多执行 12 条相关性 query，另有最多 4 条精确查找。当前只要任一相关性 query 失败就标记 `succeeded_partial`，前端将其与真正的核验不足一起渲染为“部分核验阶段未完整完成”。Semantic Scholar 已有 Redis 限流、缓存和 429 重试，但无 Key 或连续 query 仍可能被限流。

### 实施方案

1. 后端为 query 记录用途：主问题、方法、反证、评估、精确查找。
2. 前端按影响分级：
   - 至少 80% 成功、已有足够候选且主问题/反证 query 未失败：运行概览显示成功；灰色 Tag 标注“外部检索 11/12，1 条受限”，详情放在可折叠日志。
   - 主问题或反证 query 失败、成功率低于阈值、候选不足：保留橙色告警。
   - 全部失败：红色失败状态。
3. 采用分阶段 query 预算：先跑主问题和高价值研究轴；候选/覆盖足够时不消耗低价值 query；尊重 `Retry-After`，把 429 留作可延后重试项。
4. 精确查找也写入审计摘要，但其单点失败不阻断主检索。

### 验收

- 11/12 成功不会出现全局“未完整完成”警告。
- 反证或主问题 query 的失败仍可见且影响等级正确。
- 运行记录可追溯每条失败 query 及其用途。

## D5：Gap 标注远程备份抽取器

### 现象与根因

`gap annotation failed validation` 表示 Ollama 已返回内容，但经过首次加两次 schema 修复后，JSON 或关系语义仍不合格。它不同于 SSH 隧道、404、超时等模型不可用错误。小模型能力可能是原因，但论文核心 Markdown 信息不足也会导致无有效标注。

### 实施方案

1. 先按 `validation_errors` 统计 JSON、Schema、关系方向、标签一致性等失败类型，并用人工标注小集评估主模型有效率和语义准确率。
2. 定义 `GapExtractor` Protocol：主实现保留 zf 微调 Ollama；远程实现仅作为 feature flag 控制的备份。
3. 仅在主模型完成现有修复仍失败，或模型服务不可用时，调用支持 JSON Schema/结构化输出的远程 API。
4. 备份结果必须走相同 validator；保存 provider、model、attempts、fallback_reason，并在 UI 显示“远程降级候选”。
5. 发送论文 Markdown 前提供显式开关和说明；未授权或无 Key 时保持本地失败可重试，不静默外发。
6. 对真正不适合 Schema 的论文区分“内容不足/不适用”，不无限重试或强制生成空白。

### 验收

- 主模型成功仍优先使用本地抽取。
- 远程备份不会绕过 Schema、workspace 隔离或来源记录。
- 用户可分辨“隧道故障”“模型输出不合格”“论文不适用”。
